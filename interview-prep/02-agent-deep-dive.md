# 02 · Agent 工具调用（升级版：真实工具 + 记忆 + 评估）— 深挖文档

> 基于 `agent_resume.py` / `agent_memory.py` / `eval_agent.py`（2026-09-29 升级）整理。面试讲 Agent 能力的核心文档。
> 升级动因：原 Demo（数学工具）被客观评估判定为"玩具工具、无记忆、无评估"——按差距清单改造为求职场景真实工具。

---

## 一、项目一句话定位

**实现"大模型自主调用真实工具"的 Agent 核心链路：模型解析任务 → 按 JSON 协议决定调用哪个工具 → 参数校验 → 执行 → 结构化结果回填模型 → 自纠错循环；附短期+长期记忆（多轮）与离线评估（100% 正确率）。**

30 秒开场版（升级后）：
> "我做了一个求职助手 Agent。三个真实工具：简历文本五维评分、岗位质量评估、JD 关键词抽取——都是纯规则、可解释、解决真实求职问题。核心链路是 JSON 协议调用：模型决定调哪个工具，我的参数守卫拦截所有坏输出并把具体错误回填给它自纠错重试。同时做了记忆——短期记住最近几轮对话、长期记住关键事实（比如你叫什么、想投什么方向）——还有离线评估，守卫和 JSON 提取 12 个用例全过。"

> 为什么弃用原来的数学工具（面试必问）：那是最典型的"为 Agent 而 Agent"——add/multiply 没有真实业务意义，面试官一眼看穿。换成求职场景工具后，每个工具都能解释"解决谁的什么问题、为什么这么设计"。

---

## 二、核心概念（先讲清楚再讲实现）

**Agent（智能体）是什么**：不只是"回答"，而是"规划 → 调用工具 → 观察结果 → 继续行动"的循环。

**Tool Use 的本质**：
```
用户请求
  → 模型判断：要不要工具？调哪个？传什么参数？
  → 按协议输出（JSON：{"tool": "score_resume", "args": {"text": "..."}}）
  → 你的代码解析 + 校验 + 执行
  → 把结果回填给模型（"评分 78 分，缺量化数字"）
  → 模型继续回答或继续调用
```

**ReAct 循环**：Reason（推理）→ Act（行动）→ 观察结果 → 再推理。Tool Use 是 ReAct 的工程落地。

## 三、实现要点（背这些，面试官深挖的就是这里）

### 1. JSON 协议设计（为什么是 JSON）
- 模型输出必须**结构化**，才能被程序安全解析和执行
- JSON 是最通用格式：模型输出稳定、Python 直接 json.loads
- **协议合同**：定义工具名枚举（score_resume / assess_job / extract_keywords）+ 参数 schema（类型、必填）——这就是"参数合同"

### 2. 真实工具（纯规则、可解释、不依赖 LLM）⭐ 升级核心
| 工具 | 干什么 | 为什么真实 |
|---|---|---|
| `score_resume(text)` | 简历五维评分：量化/项目深度/技能明确/可验证 + 简洁度，返回总分+建议 | 求职场景真实需求；纯规则可解释（每条加分逻辑能讲） |
| `assess_job(text)` | 岗位质量评估：规则扣分（JD 过短/缺职责/疑似异常），verdict 分级 | 复用 OfferAgent `job_quality.py` 同思路，可讲"和我的产品一脉相承" |
| `extract_keywords(text)` | JD 关键词 Top8（词频+停用词过滤） | 投递前看岗位要什么，可解释 |

**为什么用纯规则而不是 LLM 实现**：工具执行必须确定性、零成本、可测试——LLM 实现会让工具本身不稳定，违背"程序兜底"原则。面试加分点。

### 3. 参数守卫（5 类坏输出拦截）⭐ 核心亮点
```
模型输出 → 依次检查：
① 非法 JSON      → 解析失败 → 反馈"输出不是合法 JSON"
② 非对象         → 顶层不是 dict → 反馈格式要求
③ 未知工具       → tool 不在枚举里 → 反馈可用工具列表
④ 缺参数         → args 缺少必填字段 → 反馈缺哪个
⑤ 类型错误       → 参数类型不符 → 反馈期望类型
→ 全部通过才执行 → 结果回填模型
```

**为什么这很重要**：大模型输出**不稳定**，生产中必须假定"模型会犯错"，用程序兜底——这就是"Agent 工程化"和"调用 API 的 demo"的区别。

### 4. 错误回填 + 自纠错循环
- 校验失败 → 把**具体错误信息**（不是笼统的"错了"）反馈给模型 → 模型修正输出 → 再校验
- 关键：**错误信息要具体**（"缺少参数 text" 而不是 "格式错误"），模型才能改对

### 5. 记忆（短期 + 长期）⭐ 升级核心
- **短期记忆**：最近 N 轮对话窗口（`Memory.turns`，滑动淘汰），注入 system prompt 的"【最近对话】"
- **长期记忆**：规则抽取事实表（`Memory.facts`：我叫/学校/求职方向/做过项目），跨轮保留，注入"【我记住的关于你的事实】"
- 设计取舍（面试讲）：全量历史简单但贵且撑爆上下文；窗口滑动控制成本；事实抽取让关键信息跨会话存活；超长时用 LLM 压缩摘要

### 6. 评估（有数据 = 有优化过程）⭐ 升级核心
`eval_agent.py`：
- 守卫拦截率：6 类输入（2 正常 + 4 坏）→ 6/6 判定正确
- JSON 提取成功率：6 种回复格式（纯 JSON/夹文字/嵌套/无 JSON/不完整/非对象）→ 6/6
- 端到端：3 条真实 LLM 用例（工具调用/记忆追问/换工具）
- 面试说法："离线评估 100%（12/12），证明了协议和守卫的正确性；端到端验证真实链路"

### 7. 当前局限（主动讲）
- 工具只有 3 个、规则简单（评分是关键词计数，不是语义理解）
- 记忆是规则抽取，不是语义抽取（复杂事实抽不准）
- 评估集小、端到端依赖 API 稳定
- 无多工具链式编排（"先评分再给建议"由模型多轮完成）

## 五、20 个面试深挖问题

### 概念
1. **Agent 和普通 chat API 调用的区别？** → 普通调用：一问一答；Agent：模型可以"决定行动"（调工具），程序执行后回填，形成闭环
2. **什么是 ReAct？** → Reason + Act 交替；推理决定行动，观察结果再推理；你的实现就是它的工程化
3. **为什么工具调用要结构化输出？** → 程序才能可靠解析；JSON 通用 + 可校验
4. **Function Calling（OpenAI/DeepSeek 原生）和你手写 JSON 协议的区别？** → 原生：平台约束输出格式（tools 参数）；手写：自己控制一切（校验、重试、兼容任意模型）。**能讲出区别 = 真懂**

### 实现
5. **参数守卫怎么设计？** → 5 类错误分级检查；错误信息具体化回填
6. **模型输出非法 JSON 怎么办？** → 解析失败 → 把错误位置/原因反馈 → 重试（有上限）
7. **自纠错循环会不会死循环？** → 加最大重试次数（你设的 2-3 次）；超出返回错误给用户
8. **工具执行失败（比如除零）怎么办？** → 和校验失败同理：具体错误回填模型
9. **并发安全？** → 当前单会话无状态；加了记忆后注意**会话隔离**（每会话独立 Memory 实例，不共享事实表/窗口）——面试可主动讲这个设计考虑
10. **怎么防止模型乱调工具？** → 协议约束（只有 3 个白名单工具）+ 校验拦截 + prompt 明确"只有必要时调用"

### 与业务结合
11. **你的 OfferAgent 用到 Agent 了吗？** → 部分：话术生成有"生成→校验→重写"循环（check_talk + 禁用词重试）——这是你 Demo 错误回填思想的迁移，**主动讲这个关联**
12. **记忆有哪些实现方案？** → 全量历史（简单、贵）、摘要压缩、向量检索历史（长期记忆）；说出取舍
13. **多轮规划怎么防止"模型绕圈"？** → 最大轮数 + 超时 + 检测重复动作
14. **Agent 失败最常见的三个原因？** → 输出格式不稳定、工具行为超出预期、错误信息不具体导致重试无效

### 短板与延伸
15. **你这 Agent 最大局限？** → 工具规则是关键词计数（不是语义理解）、记忆是规则抽取（复杂事实抽不准）、评估集小、无多工具链式编排——但协议/校验/回填/记忆/评估链路完整，能讲清楚"已知短板 + 下一步改法"
16. **真实生产 Agent 还差什么？** → 记忆、规划、多工具编排、错误观测（日志/追踪）、权限控制、成本控制
17. **和 LangChain 的 Agent 比？** → LangChain 封装了工具注册/解析/执行；我的更底层的理解是它的基础——能讲 = 加分
18. **如何评估 Agent 好不好？** → 任务成功率、平均轮数、错误类型分布、成本；你说"记录失败案例"就是评估雏形
19. **Agent 的安全边界？** → 工具白名单、权限最小化、敏感操作人工确认、日志审计
20. **下一步方向？** → 记忆 + 多轮（W2 在做）→ 真实工具 → 子 Agent 协作 → 评估体系
