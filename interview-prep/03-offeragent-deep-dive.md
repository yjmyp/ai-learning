> 基于 offeragent/ 真实代码整理。面试定位：**产品思维 + 用 AI 解决自己真实问题**。

> 同日第二批：**匹配分门禁（GATE_SCORE）+ 记忆落盘 SQLite（跨会话）+ 多 Agent 协作（主管分派角色化子 Agent：岗位分析师 / 话术专家 / 投递复盘员）**。

## 一、项目一句话定位

**一个求职 Agent 工作台：先用"自我蒸馏（Self-Distill）"把用户画像建起来，再做岗位匹配、话术生成、数字分身，形成"认识自己 → 找岗位 → 投递 → 复盘 → 更新自己"的闭环；2026-09 升级为真正的 Agent——模型自主规划工具链（质量评估→JD拆解→匹配→话术→校验→投递），执行类动作停在人确认。**

30 秒开场版：
> "我做了一个求职 Agent，差异化在 Self-Distill——市面上求职工具直接做岗位匹配，我先用结构化素材蒸馏出用户画像，所有下游都基于它。最近我做了一次真正的 Agent 化升级：原来是我在界面上点按钮触发函数，现在是模型拿到一个任务自己规划工具链——评估岗位质量、拆 JD、算匹配度、生成话术、校验，最后打开投递链接前停下来等我确认。它自己跑完了 10 家岗位的匹配和话术，最高匹配 88%。"

## 二、系统架构（数据流）

```
① 素材(me.txt: 经历/技能/项目/约束)
   │  self_distill / distill
   ▼
② 画像(结构化: 基本信息/技能/项目/约束)
   │
   ├──→ 岗位库(jd_fetcher/job_sources: 多来源抓取 + 质量检查)
   │       job_quality: 7 规则打分(防假岗/僵尸岗)
   ├──→ 匹配(PROMPT_MATCH: 结构化报告 + 匹配度%)
   │       v41.batch_match: 批量跑 + 正则抽分回填
   ├──→ 话术(prompts.py: BOSS/邮件/内推三版 + 禁用词校验重试)
   ├──→ 数字分身(digital_twin: intro/反问/扮演我/复盘/进化/雷达)
   └──→ 投递追踪(v41: 链接检测/漏斗图/周趋势/面试提醒)
   │
   ▼
③ 复盘闭环: reviews.jsonl → evolve_profile → 回写画像 → 再匹配

④ Agent 引擎层（2026-09 新增，offer_agent_core.py + offer_agent_tools.py）
   用户给目标 → 模型自主规划 → 依次调用工具 → 根据结果继续 → 停在人确认
   工具注册表（8 个）：assess_job / split_jd / match_job / generate_talk
                    / check_talk / funnel / needs_followup / open_application🔒
   复用：agent_tool_guard.safe_call（参数守卫）+ agent_memory.Memory（记忆）
   门禁：match_job 带 GATE_SCORE=60 裁决（建议投 / 不建议投），日志带 verdict
   记忆：Memory(db_path=SQLite) 跨会话持久化（facts/turns 双表）
   多 Agent（offer_agent_multi.py）：主管(dispatch) → 岗位分析师 / 话术专家 / 投递复盘员
```

## 三、关键模块与设计决策（面试深挖点）

### 1. Self-Distill（差异化核心）⭐ 必讲
- **为什么先蒸馏自己**：市面产品（Resume-Matcher 等）拿到简历直接匹配 → 匹配是黑盒；我先用**素材 → 画像**，画像是一切下游的地基
- **画像结构**：基本信息 / 技能 / 项目 / 工作方式 / 求职目标 / 硬约束（到岗时间、天数、时长、地点）——**约束单独成块**，匹配时"硬约束不匹配直接降权"
- **合规原则**：画像只来自素材事实，禁止编造

### 2. 岗位质量检查（job_quality.py）
- **纯规则，不调大模型**：快、免费、可解释、结果稳定
- **7 条规则**（每条有依据）：
  1. JD 过短（<60 字）→ 缺信息
  2. 无公司名（company#xxx 占位）→ 平台没返回
  3. 薪资区间过宽（上限>下限×5）→ 虚标
  4. 薪资偏低（一线/新一线 <80/天）→ 不靠谱
  5. JD 模板复读（有职责+要求但 <200 字）→ 复制粘贴岗
  6. 发布时间 >60 天 → 僵尸岗
  7. 无详情链接 → 无法核对
- **分数机制**：100 分起扣，每规则有 penalty，输出 flags（问题+证据+扣分）→ **可解释**："为什么这个岗位 62 分，因为 JD 只有 40 字"

### 3. 话术生成（prompts.py，v5 迭代）⭐ 讲迭代过程
- **v2 失败**：三段式结构 → 逼模型写简历摘要 → 生硬
- **v3 失败**：过分口语（"想问问""聊聊"）→ 不像正常求职沟通
- **v4 失败**：结构+禁用词表仍逼出工整求职信
- **v5 标准**：像真人手机打字——短、直接、只带一条最相关细节、自然收尾
- **禁用词机制**：`check_talk` 命中禁用词（"期待您的回复""高度匹配""学习能力强"等 40+）→ 带具体反馈重写（最多 2 次）——**这就是你 Agent Demo"错误回填自纠错"思想在产品里的应用**
- **BOSS 极简版**：不写项目不写数字，一句话"我是 XX 学校 XX 专业 2027 届，想投 XX 岗，以下是我的简历"——用户要求的"直接了当"

### 4. 数字分身（digital_twin.py，合规版）⭐ 差异化
- 6 能力：intro（30/60/90 秒定制自我介绍）/ questions_to_ask（10 反问，分四类）/ twin_answer（"扮演我"只答画像内事实）/ save_review（复盘入库）/ evolve_profile（复盘提炼→回写画像）/ job_radar（反向岗位雷达）
- **合规红线**：不是替你面试，是替你"准备与复盘"；只基于画像事实回答，画像没有的明确说"还没准备好"——**这个边界要主动讲**（体现工程伦理意识）

### 5. 批量匹配（v41.py）
- 对"待投且未匹配"岗位一次跑完；正则从报告首行抽匹配度回填 meta → 列表直接排序
- 配套：链接有效性检测（投递前重访 URL）、投递漏斗图、周趋势线、面试日历提醒、投递三件套（简历 PDF + 上线链接 + GitHub）

### 6. Agent 引擎（offer_agent_core.py，2026-09 升级）⭐ 必讲：从"应用"到"真 Agent"
**为什么原来"不算 Agent"**：原来 = 人在界面上点按钮 → 触发某个函数（如"批量匹配"）→ 模型单次回答。模型没有"自主决定、按顺序编排、根据中间结果继续"的闭环。
**升级后**：用户给一个目标（"帮我把 Calix 这个岗位处理一遍"）→ 模型自己规划并依次调用工具链：
```
用户任务 → 模型决定: assess_job → split_jd → match_job → generate_talk → check_talk → open_application🔒
每个工具结果回填 → 模型判断下一步 → 执行类动作停在用户确认 → 确认后继续 → 最终汇总
```
- **工具注册表（ToolRegistry）**：统一 schema（name/description/params/human_confirm），模型从注册表发现工具——借鉴 OpenAI Agents SDK
- **状态对象（AgentState）**：messages + 记忆 + trace + 预算——借鉴 LangGraph 的 State
- **安全边界（human_confirm）**：执行类动作（打开投递链接）必须停在人确认，发送前那一下永远由人做——借鉴 Nvidia OpenShell 的权限分级
- **可观测（trace）**：每一步"模型调了什么工具、参数、结果、成败"都记录，可导出——面试讲"Agent 要有日志和评估"
- **复用而非新造**：守卫复用 agent_tool_guard.safe_call，记忆复用 agent_memory.Memory；8 个工具全部是 OfferAgent 现有函数包装，一行新业务逻辑都没写——"工具就是你的产品能力"

## 四、当前短板（主动讲，别等面试官戳）

1. **匹配是"prompt 输出"，不可解释**：88% 怎么来的？只有大模型知道 → **下一步改结构化打分**（字段抽取 → 维度加权 → 可复算）
2. 功能多但深度分散：批量/漏斗/提醒是"工程面"，不是"算法深度"
3. 数据规模小：10 家岗位、单一用户画像——统计结论不成立，只当产品演示
4. 界面/部署是 Streamlit 单机：无用户系统、无并发（L1 密码门已做，但没有真正多用户隔离）
5. Agent 引擎的局限（已解决 → 剩余）：子 Agent 协作、跨会话记忆、匹配分门禁**已做**；剩余：LLM 工具是嵌套调用（成本 x2）、无真正的"多轮跨任务长程规划"（budget 上限内单任务）、子 Agent 结果只回传摘要（详情需另查）

## 五、第 2 周深度化任务（W2 主线）

**匹配逻辑结构化打分**（把"AI 说的 88%"变成"可解释的 88%"）：
```
字段抽取(规则+LLM辅助) → 维度打分 → 加权求和 → 输出解释
维度示例：技术栈 30% / 项目匹配 25% / 网络背景 15% / 地点 15% / 时长 15%
每条扣分带证据："时长：JD≥6个月 vs 画像3-6个月 → 扣 10 分"
```
- 保留大模型生成"匹配点/差距"文本（可读性），但**分数必须可计算**（纯规则可复算）
- 验收：对同一岗位跑 3 次，分数不变（确定性）——这就是"工程化"和"prompt 碰运气"的区别

## 六、20 个面试深挖问题

1. **这个项目和 Resume-Matcher 等开源项目比，你的差异化？** → Self-Distill（先画像后匹配）+ 数字分身 + 复盘闭环；参考过它们但核心设计不同
2. **自我蒸馏解决了什么问题？** → 简历/素材是零散事实，画像把零散事实结构化；匹配/话术/分身都复用同一画像，一致性
3. **匹配度 88% 怎么算的？** → 目前是大模型结构化输出提取的百分比，**承认不可解释**，正在改结构化打分（讲 W2 方案）
4. **岗位质量规则为什么不用模型？** → 规则可解释、免费、快、稳定；模型可能"拍脑袋"
5. **话术 v5 和 v2 差在哪？** → 讲迭代失败史（v2 生硬→v3 太随意→v4 仍像模板→v5 像真人）；面试官爱听"你从失败里学到了什么"
6. **禁用词机制本质是什么？** → 生成后校验 + 具体反馈重试 = 程序兜底模型不稳定（呼应 Agent Demo）
7. **数字分身能替我去面试吗？** → **不能，也不应该**：合规边界——它只做准备与复盘；替面是身份冒充。主动讲这个 = 加分
8. **数字分身怎么保证不编造？** → 只基于画像事实；画像来自素材蒸馏；未知就明说；双层约束
9. **复盘闭环怎么运作？** → reviews.jsonl 记录 → evolve_profile 提炼"被认可/被挑战" → 回写画像 → 影响后续匹配
10. **批量匹配的工程细节？** → 正则抽分（匹配度[:：]?(\d{1,3})%）、meta 回填、进度反馈；失败单条不中断
11. **多来源抓岗位怎么做？** → job_sources/jd_fetcher 多平台；解析失败降级；缺字段（company/url）用 meta 回填——**讲过修复：公司/链接丢失导致质量分误伤**
12. **为什么做投递漏斗图/周趋势？** → 数据驱动投递节奏：看转化率而不是凭感觉
13. **数据存在哪？** → JSONL 追加（applications.jsonl/reviews.jsonl）+ meta.json；简单可审计；为什么不用数据库（单机够用）
14. **L1 密码门是什么？** → 哈希密码门控（v41.hash_password）；防止公开部署后他人看你数据；知道多用户方案（真正账号系统）是下一步
15. **这个项目对求职者真实价值？** → 结构化知道自己 → 高效投递 → 复盘进化；我实际用了：10 家岗位、最高匹配 88%（南京 Calix）
16. **你最想改进什么？** → 匹配可解释性（W2 在做）+ 岗位数据实时性（抓取依赖平台开放程度）
17. **和 RAG 项目的关系？** → 复用：数字分身/画像本质是"用 LLM 做信息结构化"；未来可给画像加 RAG 检索历史复盘
18. **如果岗位很多（100+），哪里先崩？** → 匹配成本线性涨（每岗一次 LLM 调用）→ 方案：先规则预筛（job_quality+关键词）再 LLM 精匹配
19. **如何防止投递话术千篇一律？** → 每个岗位用"画像+该岗位 JD"生成（不是模板填空）；禁用词校验保证不像 AI
20. **商业化还差什么？** → 真实用户系统/隐私、岗位数据源稳定授权、匹配效果评测、简历生成；诚实说"目前是个人工具"
21. **你的 OfferAgent 真算 Agent 吗？（可能被直接问）** → 以前不算（人点按钮+单次调用）；9 月加了 Agent 引擎后算：模型自主规划工具链、按中间结果决定下一步、执行类动作停在人确认、全程 trace。**讲"怎么判断一个东西算不算 Agent"= 有没有自主闭环**
22. **Agent 引擎参考了市面哪些设计？** → LangGraph（状态对象/循环控制）、OpenAI Agents SDK（工具注册表）、Nvidia OpenShell（工具白名单 + 执行动作需确认）；**自己落地的是最小但完整的闭环**
23. **执行类工具为什么要人确认？** → 安全边界：投递是不可逆外部动作，发送前那一眼必须人看；生产 Agent 的安全原则（工具分级、最小权限）
24. **Agent 的 trace 有什么用？** → 可观测性：每步工具调用有日志，出问题能回溯；也是评估的基础（成功率、平均轮数、错误分布）
25. **匹配分门禁（GATE_SCORE）是什么？** → match_job 工具返回 `verdict`（≥60 建议投 / <60 不建议投 / 无分待评估），日志带裁决列——"机器给结论、人做决定"；避免低匹配岗位浪费时间；面试讲"这是把 Agent 从玩具推向可用的工程护栏"
26. **记忆为什么从内存改 SQLite？** → 进程内记忆关掉就丢；SQLite 落盘后**跨会话记住用户事实**（facts 表 + turns 表，facts 用 INSERT OR IGNORE 去重）；无 db_path 保持纯内存、向后兼容——这是"长期记忆 vs 短期记忆"的工程化
27. **多 Agent 怎么做的？** → 主管-子 Agent 模式：主管只有 dispatch 一个工具，拆解任务分派给角色化子 Agent（岗位分析师/话术专家/投递复盘员），每个子 Agent 是独立 run_agent 实例（独立状态、独立工具集、独立角色提示词）；**投递动作（open_application）不在任何子 Agent 工具集里，永远人确认**——参考 LangGraph supervisor pattern / CrewAI role-based；实测主管能自主完成"分析→话术→截断自动重派→汇总"
28. **多 Agent 跑出来的坑？** → 两个：① 主管第一轮输出了 DSML 标签而不是 JSON → 在角色提示词里强制"只输出一行 JSON"；② 子结果摘要被截断导致话术专家反复重试 → 识别为"模型自纠错"特性而非 bug；讲出来体现"真跑过、真修过"
29. **多 Agent 批量在 Web 端怎么用？** → Agent 页"运行模式"radio 切单/多 Agent，批量跑所有待投岗位跟随模式，结果统一落盘 + 裁决列——一个入口两种编排

## 八、Agent 四层框架对照（2026-10-08 补充，面试用来"自己给自己挑毛病"）

> 用法：面试官问"你这个 Agent 做到什么程度"时按这四层回答——**说清哪层有、哪层是手工版、哪层还缺**，比笼统说"我做了个 Agent"专业得多。

| 层 | 概念标准 | 我的现状（有代码可查） | 缺口 | 补法（按性价比） |
|---|---|---|---|---|
| **Planning** | ReAct / CoT / Plan-and-Execute / 任务拆解 | `offer_agent_core.py`：工具注册表 + 状态对象 + ReAct 循环 + **预算上限防死循环**；trace 可复盘 | 只有 ReAct（边走边看），**没有显式 Plan 阶段**，不能先给用户一份"我打算这么干" | 加 `plan()` 节点：先输出 3-6 步计划（每步用哪个工具）→ 人确认 → 逐步执行；过程可解释、可中断 |
| **Memory** | 短期=上下文；长期=向量库/数据库 | `agent_memory.py`：SQLite 事实表 + 短期对话，跨会话不丢；单一权威源 `meta.json`（分数只存一处） | 长期记忆是键值式，**没有语义检索**（"上次那个高匹配的南京岗位"要靠翻） | 记忆 embedding 化：事实/复盘写入向量库（复用 RAG v3 的向量层），按语义召回 top-k 记忆注入上下文 |
| **Tool** | Function Calling + MCP + 工具守卫 | 8 工具统一 Schema；**参数合同拦 5 类坏输出**（非法 JSON/未知工具/缺参/类型错/非对象）；错误回填自纠错；执行类工具 `human_confirm` 硬闸 | 没接 **MCP**，工具不能复用生态 | 写最小 MCP server，把现有 8 工具暴露成 MCP 工具（半天），可讲"工具层同时支持内置注册表与 MCP 两种来源" |
| **Reflection** | 自评-修正 + 评估集 | 评估脚本（守卫 6/6、提取 6/6）；话术生成后**自动校验禁用词并重写**（一次 reflection）；失败回填错误重试 | 没有**任务级自评**（结束时不自查"目标达成没"）；没有**回归评估集**（改提示词不知道变差没有） | 加 `reflect()` 节点（自评目标/证据/下一步）+ 20 条 Agent 回归用例（输入任务 → 期望工具序列） |
| **工程化** | trace / 权限沙箱 / 并发 / 成本 | trace 落 JSONL；批量打分用**线程池 3 并发**（写回主线程防竞争）；投递前链接核验（404 拦截） | trace 只有文件**没可视化**；**没有成本计量** | trace 可视化时间线 + 成本聚合（照 RAG v3 的 `trace.py` 写法） |
| **部署** | FastAPI / Docker / Secrets / 云端 | Streamlit Cloud + Secrets 管密钥 + 数据落盘 | **没 Docker 化**，服务层是 Streamlit 不是 API | 照 `rag2/Dockerfile` + `docker-compose.yml`（已跑通）搬：FastAPI 包一层 + compose 起服务 |

### 8.1 框架对标话术（被问"用没用 LangChain/LangGraph"时）

> "我没用框架，但自研引擎对上了 LangGraph 的核心概念：**显式状态对象**（≈ StateGraph 的 state）、**工具即节点 + 条件边**（ReAct 循环）、**人机检查点**（`human_confirm`，≈ interrupt）、**可恢复**（trace JSONL + SQLite，重启能接着讲走到哪一步）。选自研是因为我要能改每一层、能加断言、能测；换 LangGraph 我反而说不清瓶颈在哪——但团队若已在用，我一天能迁过去，因为概念是对齐的。"

**生态现状（主动说一两句，证明在跟）：**
- **LangGraph**：生产级事实标准（图编排/显式状态/checkpoint/人机检查点）——我的自研引擎是它的手工版
- **CrewAI**：Role/Goal/Backstory 角色团队，快速原型（我的 Supervisor 多角色思路一致）
- **AutoGen**：⚠️ 已进入维护模式，微软转向 Agent Framework——**"新项目我会避开 AutoGen"** 是加分句
- **OpenAI Agents SDK**：LiteLLM 支持 100+ 模型，上手最快
- **LangChain / LlamaIndex**：前者是生态底座（企业用得多），后者偏 RAG
- **Mastra**（TS/Next.js 首选）/ **OpenHands**（开源代码 Agent）
- **Dify / Coze / 华为 AgentArts**：国内低代码落地主流

### 8.4 四层框架的补齐结果（2026-10-08 晚，代码已合入并测过）

| 层 | 补了什么 | 关键实现 | 验证 |
|---|---|---|---|
| **Planning** | `offer_agent_plan.make_plan()` | 先出 3-6 步计划（每步：工具 + 目标），并**校验工具名**——模型编造的非法工具会被单独标出来，不静默失败 | `test_agent_v3.py` 11/11 |
| **Reflection** | `offer_agent_plan.reflect()` | 收尾自评 `goal_met / evidence / gaps / next_action`；**解析失败给保守值（goal_met=None），不假装成功** | 同上 |
| **Tool（MCP）** | `offer_agent_mcp.py` | 手写 MCP server（stdio + JSON-RPC 2.0）：`initialize / tools/list / tools/call`，暴露 10 个工具，执行类工具带 `humanConfirm` 标注 | 真起子进程跑协议 |
| **Memory（语义）** | `offeragent/memory_vec.py` | 长期记忆向量化（bge 语义召回，支持模糊指代），三档自动降级（bge → TF-IDF → 词面）；`context_block()` 注入 Agent system | 语义召回命中测试 |
| **工程化** | `agent_trace_view.py` | trace 可视化页：运行次数 / 平均步数 / **工具调用分布** / 工具覆盖率 / 每次运行时间线（步→工具→参数摘要→结果） | 页面实测渲染 |
| **部署** | `offeragent/Dockerfile` + compose | 构建上下文=仓库根、非 root、healthcheck、data 挂 volume、密钥走环境变量 | `test_docker_static.py` 12/12（本机无 Docker，仅静态校验） |

**两个踩坑（都是"卡住/报错"型，讲出来很加分）：**
1. **加载 bge 前必须设 `HF_HUB_OFFLINE`**：不设的话模型会去 HuggingFace 查版本，网络不通时不是抛异常而是**卡死几分钟**——这次真卡了 10 分钟才定位到；解决办法是"先检查本地缓存有没有模型，有才走向量档，没有直接降级到 TF-IDF"。
2. **MCP 必须强制 UTF-8**：Windows 控制台默认 GBK，服务端输出中文后客户端按 utf-8 解码直接 `UnicodeDecodeError`；协议层是 UTF-8，这条不能含糊。

**新增追问：**
| 追问 | 答法要点 |
|---|---|
| 你的 MCP 是自己实现的，凭什么说合规？ | 我实现了协议子集：`initialize` 返回协议版本与 capabilities、`tools/list` 返回 JSON Schema、`tools/call` 返回 `content[].text` 与 `isError`，执行类工具用 annotations 标注 humanConfirm；并用客户端脚本走完整握手 + 错误分支验证。没接真实客户端这一点我会明说。 |
| 记忆用向量是不是过度设计？ | 键值记忆只能精确匹配，"上次那个高匹配的南京岗位"这种就查不出来；用向量是为了支持模糊指代。但它有三档降级（没有模型就走 TF-IDF/词面），所以不构成部署风险。 |
| Plan 阶段会不会拖慢任务？ | 多一次模型调用（约 1s）；收益是过程可解释、可提前拦掉错误路线。我的默认是"先计划再执行"，并保留 ReAct 作为执行层的推进方式。 |

**90 秒**：
> "OfferAgent 是我的求职工作台，核心差异化是 Self-Distill：先用结构化素材蒸馏出自己的画像——基本信息、技能、项目、硬约束，所有下游都基于它。岗位库抓取后先过 7 条质量规则筛掉僵尸岗，再做匹配输出结构化报告，话术按 BOSS/邮件/内推三个场景生成，带禁用词校验和重写。还有个合规版数字分身：自我介绍、反问清单、扮演我回答、面试复盘回写画像，形成闭环。今年 9 月我做了一次关键升级——Agent 化。原来是我在界面上点按钮触发函数，现在用户给一个任务，模型自己规划工具链：评估岗位质量、拆 JD、算匹配度、生成话术、校验，最后打开投递链接前停下来等我确认。这个引擎参考了市面框架的模式（LangGraph 的显式状态与检查点、AutoGen 已进维护模式所以要避开），但都是我自己实现的最小完整闭环：Plan 出计划并校验工具名、Reflect 收尾自评、MCP 工具层暴露 10 个工具、长期记忆向量化召回，全程有 trace 日志可以复盘每一步。它帮我跑完了 10 多家岗位，最高匹配 88%。最近我把匹配分数从'模型直接给分'改成了五维结构化加权——同一岗位跑 5 次，旧法标准差 3.31 分、最大波动 10 分，新法 0.00 分，分数可复算、每个维度都能给出命中或缺失的证据。"

### 8.5 生产级/商业化就绪度（2026-10-08 补齐）

被问"这东西能上线吗、离商业化多远"，别用形容词，给分层结论 + 证据：

完整评估（含判定标准、逐项证据、剩余缺口、复现命令）写在 **`offeragent/docs/production_readiness.md`**，这里给三句话版本：

1. **技术侧已经到生产级**：可部署（Docker+compose、配置走环境变量、数据挂 volume）、可观测（trace 给你运行次数/步数/工具分布）、可验证（`run_tests.py` 18 通过 0 失败 + CI 三档）、安全（密钥门禁测试保证密钥不随代码进仓库）。
2. **产品侧还停在"单人工具"**：现在所有用户共享一份 `data/`（简历、画像、投递记录），只靠一个访问密码。
3. **商业化硬阻塞有两个**：多用户数据隔离（2-3 天工作量）和隐私合规（隐私政策 / 用户协议 / 数据删除入口，1 天）。这两件不做完，不能给陌生人用。

**程度口径**：当技术作品 100% 达标；给陌生人当小工具约 60%；当能赚钱的产品约 30%（还缺付费闭环与数据源稳定性）。
**讲法**："我知道它技术上到哪了、产品上缺什么，缺的两项是非技术但必须做的：账号与数据隔离、隐私合规。"
