# 数据采集方式全景（OfferAgent 搜岗用到的与故意不做的）

> 目的：把"从别的平台/渠道拿岗位信息"这件事说全，并标明**哪些已经接进 OfferAgent、
> 哪些故意不做、为什么**。判断标准是三条：能不能被平台接受（ToS）、有没有封号/法律风险、
> 值不值得为它维护一套反爬对抗。

## 一、13 种方式（按"正规程度"从高到低）

| # | 方式 | 是什么 | 合规性 | OfferAgent 状态 |
|---|---|---|---|---|
| 1 | **官方 API（付费/注册）** | 平台主动开放、要 token、有配额 | ✅ 最正规 | 部分：Greenhouse（见 3） |
| 2 | **公司自有招聘系统 API（ATS）** | 公司把职位挂在 Greenhouse / Lever / Ashby / Workday，这些系统有公开 JSON | ✅ 完全正规 | ✅ **已接入**：`search_greenhouse`（Anthropic 等 7 家 AI 公司） |
| 3 | **公司招聘站公开接口** | 腾讯/网易这类自建招聘站，网页调的就是公开 JSON | ✅ 正规 | ✅ **已接入**：`search_tencent` / `search_netease` |
| 4 | **公开聚合/远程岗 API** | RemoteOK / Arbeitnow / Remotive / Jobicy 这类公开 job board API | ✅ 正规 | ✅ **已接入**：`search_remoteok` / `search_arbeitnow` / `search_remotive` |
| 5 | **官方 RSS / Atom** | 站点自己发布的订阅源（WeWorkRemotely、很多社区） | ✅ 正规 | ✅ **已接入**：`search_wwr`；另支持任意 RSS（`search_custom_feed`） |
| 6 | **社区招聘贴 API** | Hacker News「Who is hiring」通过公开 Algolia API 读取 | ✅ 正规 | ✅ **已接入**：`search_hn_hiring`（只取顶层招聘贴，AI 岗密集） |
| 7 | **站点自己的搜索接口** | 页面前端调的 `/api/xxx-search`，公开、免登录 | ⚠️ 灰但常见 | ✅ **已接入**：`search_nowcoder`（牛客，实测接口忽略城市参数，所以城市在客户端过滤） |
| 8 | **静态 HTML 解析** | requests + 正则/BS4 抠页面源码 | ⚠️ 灰，低频尚可 | 部分：`extract_jobs` 支持"页面文本 → 岗位列表" |
| 9 | **无头浏览器渲染** | Playwright/无头 Chrome 跑完 JS 再读 DOM | ⚠️ 灰，资源重 | ✅ **已接入**：`search_shixiseng`（本机可用，云端无浏览器） |
| 10 | **真实浏览器 + 复用登录态（CDP）** | 连你本机已登录的 Edge，等于"你在操作、程序在旁边看" | ⚠️ 取决于平台 ToS | ✅ **已接入**：`search_boss`（BOSS 直聘，本机已登录时可用；**发送动作永远人工**） |
| 11 | **搜索引擎 API 兜底** | Bing / Brave / SerpAPI 搜 `site:zhipin.com 南京 AI 实习`，再抽结果 | ✅ 正规（付费） | ⛔ **未接入**：要付费账号 + 配额，收益不如直连接口；留作后续 |
| 12 | **邮件 / IM 转发解析** | 订阅招聘邮件、群里转发的岗位贴 → 解析成岗位 | ✅ 正规（自己的数据） | 部分：`inbox_parse` 已支持**粘贴文本**解析；IMAP 自动读邮件未做 |
| 13 | **接口逆向 / 客户端破解 / 代理池刷量** | 抓包补签名、Hook 客户端、改机、代理池轮换绕过风控 | ❌ **高风险** | ⛔ **故意不做**（见下） |

## 二、故意不做的三类，以及原因

1. **绕登录 / 绕人机验证 / 破签名（第 13 类）**：这不是"技术难"，是"风险归你"——
   违反平台用户协议、可能触犯《反不正当竞争法》《数据安全法》，账号封禁也只是最轻的后果。
   对这种站（招聘 App、部分大厂站），OfferAgent 的原则是：**能公开读就公开读，读不到就不读**。
2. **代理池大规模轮换刷量**：单次搜索几百条、自己看，和"用 100 个 IP 每小时刷 10 万次"是两件事。
   后者会直接进风控名单，且对个人求职毫无必要。
3. **自动化投递/群发消息**：OfferAgent 里所有投递动作都停在 `humanConfirm`，
   **最后一下必须人点**——这条是红线，不是能力问题。

## 四、工程上的几个细节（面试可讲）

1. **直连失败自动走代理**：`fetch_json_or_text()` 先直连、失败再探测本机代理（7897/7890…），
   也可以用 `JOBS_PROXY` 显式指定。因为"海外源在国内本机连不上、而云端在美国直连正常"，
   同一个代码要在两种网络环境下都能跑。
2. **城市在客户端过滤**：牛客接口不接受 `city` 参数（实测带/不带返回完全相同），
   腾讯/网易接口也没有可用的城市过滤 → 统一"抓回来再过滤"，并用归一化处理
   "南京市 / 江苏南京 / 魔都 / remote" 这些写法。
3. **宁可少，不要假**：严格模式下城市不匹配就整条丢掉；只有当**所有**来源都没有该城市岗位时，
   才自动放宽并明确提示"这些岗位都不是你选的城市"。
4. **每个来源都留诊断**：原始条数、保留条数、城市分布、失败原因——用户能看到"为什么只有这些"，
   而不是对着一堆结果怀疑人生。
5. **翻页深度可调 + 礼貌抓取**：界面上有「每个来源最多抓多少条」（默认 200）决定翻几页。
   实测各站总量差很多——网易同一关键词 1011 条、牛客 302 条、HN 招聘贴 782 条评论、
   Anthropic 一家 645 个职位；早期只翻 1-2 页（40-100 条）是"岗位太少"的主因。
   同一站点做了**全局节流**（两次请求的发出时间至少隔 0.25 秒）+ 并发上限 3 路，
   "并发"和"轰站"是两件事，见第六节；每次搜索都是用户主动点击触发。
6. **单页失败不整体放弃**：牛客接口偶发单页 ConnectionError，早期 `break` 导致
   302 条只拿到 80 条；现在每页重试 1 次、失败跳过该页继续翻，实测能拿满 300 条。
   每页读超时 12 秒——实测站点会偶发"整页不响应"，那种卡顿会一直挂到超时为止
   （观测到 20.87s 正好等于原来写的 20s 超时；两次尝试都挂就是 40.13s），
   收紧到 12 秒把最坏情况从 41 秒压到 25 秒左右。

## 六、并发 + 缓存实测（2026-10-10）

### 为什么做

先量化了时间花在哪：**抓 8 页牛客 = 26.6 秒，而本地解析 160 条只要 0.0011 秒
（占 0.004%）**，城市过滤 ≈0 秒。也就是说耗时几乎全是**等网络**——串行的每一秒
都是在白等，换成 Java 也一样等（RAG 服务 22 QPS、LLM 问答 1.4s 就是 DeepSeek 的网络
时间，都印证"瓶颈在网络不在语言"）。所以提速只有两条正路：

1. **并发翻页 + 礼貌节流**（`parallel_pages`）：滚动窗口保持 3 个请求在飞，
   同一站点两次请求的发出时间 ≥ 0.25s（`_throttle`，实测请求时间戳间隔 0.26s）。
   用滚动窗口而不是"一波等一波"，是因为单页偶发 ~20 秒卡顿，波次模式下它拖住一整波。
2. **结果缓存**（`data/search_cache.json`）：按「来源 + 关键词 + 城市 + 每源上限」
   存**原始来源结果**，TTL 10 分钟。城市过滤/合并去重仍在缓存之后做，
   所以同一份缓存配不同 strict_city 也都是对的。
3. **跨来源并发**（`search_all` 内，`SOURCE_WORKERS=3`）：一次搜索里的多个来源也
   并发抓（每个来源内部再各自并发翻页）。但**只有纯 HTTP 的来源能进线程池**——
   实习僧 / BOSS 要走无头浏览器 + 大模型抽岗位，而界面传进来的 `ask_model` 是
   Streamlit 里的 `ask_chat`（会读写 `st.session_state`，**不是线程安全的**），
   所以这两个来源留在主线程串行（`_parallel_safe` 判定）。合并结果仍按 sources
   的顺序输出，和串行抓取逐条一致。
4. **全局在飞名额**（`GLOBAL_INFLIGHT = 3`）：不管勾了几个来源、每个来源翻几页，
   **同时在飞的网络请求总数不超过 3**（`_NetSlot` 只加在真正发包的那一行：
   `requests.get/post` 与 `fetch_json_or_text`）。这样"总并发"是个常数——
   勾 3 个来源和勾 10 个来源对网络的压力一样，代价只是总耗时随来源数变长。
   ⚠️ 名额**只能加在最底层**：如果在 `parallel_pages` / `fetch_task` 里再包一层，
   就会出现"已经拿着名额的线程再去申请名额"，同一个信号量嵌套申请会**直接死锁**
   （3 个线程各拿 1 个、再各等 1 个，谁都动不了）。

### 实测数字

| 场景 | 耗时 | 说明 |
|---|---|---|
| 单页正常延迟 | 0.45 ~ 0.80 秒 | 24 次采样，与站点/网络有关 |
| 串行 3 页（同条件 A/B） | 1.59 ~ 1.86 秒 | 无卡顿时 |
| 并发 3 页（同条件 A/B） | 1.09 ~ 1.28 秒 | 同条件对照，约 **1.4 ~ 2.0 倍** |
| 6 页仪器化实测 | **2.30 秒** | 逐页 0.57~0.80s，请求间隔 0.26s（串行约 5~6 秒） |
| 3 来源各 200 条（冷缓存） | 17 秒 | 牛客 10 页 + 腾讯 4 页 + 网易 4 页 |
| 同条件再搜一次（命中缓存） | **0.03 秒** | 3/3 来源全部命中，完全没联网 |
| 3 来源冷抓：串行 vs 跨来源并发（同段 A/B） | 23.07 秒 → **6.04 秒（3.8 倍）** | 两轮合计；`SOURCE_WORKERS=1` 模拟串行 |
| 其中无卡顿的那一轮 | 4.99 秒 → **2.95 秒（1.7 倍）** | 干净时段才是真实倍数 |
| 全局名额 3 vs 9（3 来源冷抓，两轮合计） | 18.67 秒 vs 17.67 秒 | 基本持平——卡顿落在哪一轮才是主要变量 |
| 3 来源 / 23 个请求全挤 3 个名额（压力测试） | **5.44 秒** | 无死锁、无跳过页（牛客 15 页 + 腾讯 4 + 网易 4） |

注意：勾的来源越多，这个全局上限就越可能成为瓶颈（约 30 个请求 ÷ 3 ≈ 10 波）。
默认流程（3 个来源）实测代价≈0；若以后要一次搜 6+ 个来源觉得慢，
把 `GLOBAL_INFLIGHT` 从 3 调到 6 即可（一行常量）。

两种并发都做了结果一致性校验：**并发抓与串行抓的每个来源条数逐项相同**
（`{'牛客': 9, '腾讯招聘': 0, '网易招聘': 0}` 两轮都对得上），
所以"并发"在这里不改变结果，只改变耗时。

### 必须说清楚的波动（不能只报好看的数）

同一批实验里也出现过 **并发那次反而慢**（一次 3 页并发跑出 20.88s、40.13s）。
查下来不是并发造成的，而是**站点偶发让某一页完全不响应**：卡住的时间正好等于代码里
写的读超时（20.87s / 40.13s ≈ 一次 / 两次 20s 超时），串行抓取同样会撞上
（串行 6 页测出 25.04 秒，其中一次就占了 20.87 秒）。
所以：

- 并发**不保证每一次都更快**，但**不会把情况变坏**——同样的卡顿串行一样要等；
- 真正稳的是**缓存**：重复搜同一条件从 17 秒变成 0.03 秒，且完全不请求站点。

### 界面上的对应

「岗位库 → 🔎 关键词搜岗」有「用缓存」开关和「🧹 清空搜索缓存」按钮，
缓存条数/大小/TTL 直接显示在旁边；每次搜完显示「本次耗时 x.x 秒（其中 N 个来源命中缓存）」，
每个来源的抓取诊断里也会写明「命中缓存」还是「这次联网抓取」。

## 七、去重口径：同名岗位不是重复

实测（牛客搜「AI」深抓到 280 条）：

| 去重键 | 结果 |
|---|---|
| 岗位名 + 公司（旧口径） | **79 条** |
| 岗位名 + 公司 + 城市（现口径） | **276 条** |
| 岗位 URL | 276 条（与上一行吻合，说明差掉的 197 条不是重复） |

根因：**同一家公司会在很多城市发同名岗位**——实测「AI应用开发（可转正）@墨泊可士」
有 10 条、覆盖 10 个城市，URL 各不相同。旧口径把它们全合并成 1 条，
这是"岗位太少"的另一个真原因。现在改成「岗位名 + 公司 + 城市」：
同城跨平台重复照样合并，不同城市的真实岗位各留一条；公司名拿不到时退回 URL 兜底。

顺带修掉一个显示问题：牛客搜索接口**没有**顶层 `companyName`（那是首页版 schema），
公司名藏在 `recommendInternCompany.companyName` / `user.identity[].companyName` 里，
以前读不到就显示成 `company#304612`。

## 八、BOSS直聘：从"总是 0 条"到 120~150 条（2026-10-10）

**现象**：用户搜「AI + 南京」，BOSS直聘 **0 条**。

**根因（实测，不是猜）**：URL 里明确写了 `city=101190100`（南京），但页面返回的岗位
**全是德阳**——BOSS 前端会用它自己记的"上次选中城市"覆盖 URL 参数（那个独立 Edge profile
里记着德阳，正是当初测"未收录城市"时留下的）。岗位城市对不上 → 客户端严格城市过滤
全砍掉 → 0 条。

**改法**：不再"抓页面文本 → 大模型抽"，改成在**已登录的页面里调 BOSS 职位页自己调的接口**
`/wapi/zpgeek/search/joblist.json`——和牛客一个思路：让浏览器替我们发这个请求，
cookie / Referer 一定是对的，不用去逆向签名。城市由参数决定，返回结构化 JSON
（薪资 / 经验 / 学历 / 技能 / 公司 / 招聘者），不用大模型、支持翻页。
接口万一失败，仍退回老的"页面文本 + 大模型"那条路（并在诊断里注明它会踩城市覆盖）。

**实测**：「AI + 南京」`resCount=450`，每页 30 条。但——

**BOSS 自己的限制（我们绕，也不该绕）**：同一个会话翻到第 5~6 页时，接口回落
`{code:37, message:"您的环境存在异常."}`。把页间隔放慢到 1.2 秒也一样，说明这是它自己的
**会话级风控**，不是我们发太快。所以 BOSS 侧最多翻 5 页（约 150 条），**它说停就停**，
并把原因写进抓取诊断（`boss_limit` / `api_note`）。

**顺带修掉的两个坑**：

1. **标签页泄漏**：`cdp.close()` 关的是 **websocket 连接**，不是标签页。每抓一次页面就多留
   一个标签页，实测攒到 **52 个**之后浏览器明显变慢——一次搜索从十几秒被拖到 150 秒以上，
   看起来就是"卡死"。现在用完就关（4 个抓取函数都在 `finally` 里关）+ 超过阈值自动回收
   `close_stale_tabs()`。
2. **页面内 fetch 没有超时**：站点一挂就会一直等到 CDP 自己超时（150 秒）。
   现在单次 fetch 12 秒（AbortController）+ 整轮 60 秒上限 + Python 侧 150 秒硬上限。

**同一时刻只允许一次搜岗**：Streamlit 里换一次交互就会重跑脚本，但**上一次运行中已经在
发请求的线程不会被杀掉**（Python 线程杀不掉）。手快点两下「开始搜岗」，两批请求会同时抢
那 3 个全局名额，越点越慢。现在第二次直接拒绝并说明原因（`SEARCH_LOCK_WAIT`）。

**排查用的开关**：`JOBS_DEBUG=1` 启动 app，日志里会打出每个来源的
开始/结束/条数/耗时（`search_all` / `fetch_task` / `search_boss` 里都有），
不用再靠猜"卡在哪"。

## 九、搜岗结果丢了怎么办：磁盘快照兜底（2026-10-10）

**现象**：点「开始搜岗」→ 搜索十几秒 → 这期间页面上任何一次重跑（动别的控件 /
前端重连 / 手机切后台）都会**打断"正在跑的那次运行"**；旧运行算出来的结果只写在
当次的 `st.session_state` 里，新运行读到空 → 页面既不出结果也不报错，
实测等满 **120 秒依然是空的**（用户看到的就是"点了没反应"）。

**根因**：Streamlit 的运行是"重跑即替换"的——重跑会中断当前运行，但**Python 线程杀不掉**，
所以那次搜索其实还在后台跑、还成功了，只是它算完时所在的运行已经作废，
它写 session_state 的那一下会直接抛 `RerunException`（`BaseException`，`except Exception` 抓不到）。
结果就"消失"了。

**修法**：把"结果的归属"从某次运行挪到磁盘上。

- `search_all()` 在**返回之前**先把完整结果落 `data/last_search.json`
  （纯文件 I/O + 原子替换 + 30 分钟 TTL，见 `save_last_search()`）——
  它不碰 Streamlit，所以运行被打断也照样写得下去；搜岗本身失败（比如被搜岗闸拒绝）
  **不会**冲掉上一份好结果。
- 页面有了**唯一读入口** `pages_work._search_view()`：当次 `session_state` →
  磁盘快照 → "还在跑"提示，三级回落；从快照读回来时会如实标注
  「这是**上一次搜岗**的结果（关键词 x，n 分钟前，共 N 条）」。
- `search_in_flight()` 让界面能说清"结果不是没有，是还在跑"，并给一个
  「🔄 刷新看看」按钮。

**验收**：`offeragent/test_search_interrupt.py`（浏览器真打断一次搜岗）**8/8**；
`offeragent/test_last_search.py`（离线：读写/TTL/坏文件/失败不覆盖/页面回落）**6/6**。
